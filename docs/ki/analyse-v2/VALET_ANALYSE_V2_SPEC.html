Valet – Teil-Analyse v2

Technische Spezifikation für packages/core/src/ai/ · Stand 19.11.2026 · Grundlage: „Variante C“, verschlankt und gegen den Code geprüft

Kurzfassung. Die KI liefert in einem Aufruf wie bisher den Steckbrief (unverändert) und zusätzlich ein Profil mit 22 Feldern. Pro Teil gelten davon je nach Kategorie nur 11 bis 15. Farbwirkung und alle Matching-Werte rechnet der Code. Alle Profil-Felder stehen in einer Feldtabelle. Daraus entstehen Schema, Prüfung, Typen und deutsche Labels. Gespeichert wird in items.analysis.profile, ohne neue Spalte und ohne Migration. Das Profil ist nur zum Nachsehen da: ein schlichtes Blatt hinter einem Knopf im Steckbrief, ohne eigene Bestätigung.

1. Leitsätze

  1. Englische Keys, deutsche Labels (gilt für die ganze App, seit 19.11.2026). Code, Datenbank und KI-Schema verwenden englische Keys (fine_knit). Deutsch erscheint nur in der Oberfläche, über Labels. Neue Listen folgen dem ab sofort. Wie die bestehenden deutschen Listen umgestellt werden, steht in Abschnitt 12.
  2. Einmal analysieren, dann gilt der gespeicherte Stand. Matching liest nur gespeicherte Werte und schaut nie wieder ins Bild.
  3. Jede Eigenschaft hat genau ein Feld. Was aus vorhandenen Feldern folgt, wird berechnet und nicht gespeichert. Das Profil wiederholt keine Steckbrief-Felder: Weite und Länge stehen in fit, der Stil in styles, die Lagen in layers.
  4. Die KI schätzt nur, was echtes Bildverständnis braucht.
  5. Farben kommen weiter nur von der KI (Entscheidung 16.11.2026). Es gibt keine Pixel-Farbe. Die Farbwirkung berechnet der Code aus den HEX-Werten der gewählten Palettenfarben.
  6. Lieber leer als falsch. Ist ein Wert nicht erkennbar, bleibt er null. Gilt ein Feld nicht für die Kategorie, wird es nicht ausgewertet (Abschnitt 6.5).
  7. Menschliche Korrektur gewinnt immer. Ein bestätigter Steckbrief-Wert wird nie automatisch überschrieben. Das Profil bearbeitet niemand von Hand (Entscheidung 19.11.2026). Es gehört der KI und wird bei jeder neuen Analyse komplett ersetzt.

Umsetzung (19.11.2026): Profile ist ausdrücklich ausgeschrieben statt per Typ-Akrobatik abgeleitet (besser lesbar). Ein Test stellt sicher, dass Typ und Feldtabelle dieselben Keys haben.

Warum keine Zod-Bibliothek (abweichend von meinem ersten Vorschlag): @valet/core hängt nur von @valet/ui ab, und Zods toJSONSchema erzeugt anyOf/$schema, die Geminis strikte OpenAI-Schnittstelle nicht sicher annimmt. Die Feldtabelle bringt denselben Vorteil (eine Quelle, getypte Werte über as const) und erzeugt genau das Schema-Format, das heute läuft (type: ['integer','null'] + enum).

4.1 Schema-Regeln (Gemini, strikt)

  • Neues Unterobjekt profil (flach, required = alle Props, additionalProperties: false) und konfidenz (6 Props). Beide stehen am Ende von ANALYZE_ITEM_PROPS.
  • Zahlen nur als Ganzzahl-enum mit null. Der Bereich wird zu formality_min + formality_max.
  • Jede Beschreibung = hint + „nur für …, sonst null“, erzeugt aus einem Text je Bedingung (APPLIES_TEXT).
  • Abnahme Schritt 1: ein echter Probeaufruf mit Testkonto gegen gemini-3.5-flash-lite und beide Ersatzmodelle. Er muss gültiges JSON liefern, ohne Fehler wie „schema too complex / too many states“. Klappt das nicht, gilt diese Reihenfolge: zuerst die hints kürzen, dann konfidenz auf 3 Gruppen zusammenfassen, zuletzt Felder streichen.
  • Test: JSON-Länge des Schemas < 60 000 Zeichen (MAX_SCHEMA der Edge Function).

5.3 Pixel nur als Kontrolle (Schritt 2, klein)

Welche Farbe ein Teil hat, entscheidet die KI. Sie unterscheidet Stoff von Schatten, Glanzlicht, Logo und Futter, ein Pixel-Algorithmus kann das nicht (Beispiel: ein schwarzer Lederschuh mit hellem Glanz würde als Grau gemessen). Die Wirkung (Helligkeit, Sättigung, Temperatur) rechnet der Code aus den gewählten Palettenfarben, damit ist sie stabil und vergleichbar. Die Foto-Farbwerte, die beim Hochladen schon in item_images.colors landen, nutzt nur eine Plausibilitätsprüfung: Ist Rang 1 farbig und weicht der vorherrschende Foto-Farbton um mehr als 60° ab (z. B. KI „Rot“, Foto eindeutig blau), zeigt das Profil-Blatt „Farbe prüfen“. Zusätzlich (19.11.2026): Ist Rang 1 farbig mit Sättigung ≥ 3 (COLOR_CHECK_MIN_CHROMA) und enthält das Foto nur neutrale Farben (z. B. KI „Rot“, Foto grau), erscheint der Hinweis ebenfalls. Nur neutrale Foto-Farben ohne farbigen Rang 1 (oder bei schwach gesättigtem Rang 1 wie Marineblau, Rosa) → kein Hinweis. Die Werte werden nie automatisch geändert.

6.2 Prüfung (checkProfile, aufgerufen von checkAnalysis)

  1. Unbekannter Enum-Wert, Zahl außerhalb 1–5 oder keine ganze Zahl → null (verwerfen statt ablehnen, wie bisher).
  2. formality: beide gesetzt und min ≤ max → [min, max]; nur einer gesetzt → [v, v]; min > max → null.
  3. Listen: nur bekannte Keys, ohne Doppelte, auf max gekürzt; fehlt die Liste → [].
  4. Konfidenz: nur ganze Zahl 0–10, sonst null.
  5. Kategorie-Bedingungen: checkAnalysis setzt zusätzlich alle Felder mit !applies(ctx) auf null/[]. ctx wird aus dem erkannten Pfad, Muster und Material gebildet. So kommt nichts Unpassendes erst ins Formular.

Analysis bekommt profile: Profile, confidence: Confidence und model: string | null.

6.3 Modellname

Die Edge Function liefert schon heute { data, model }. In apps/app/src/lib/ki.ts gibt ask() künftig { data, model } zurück. analyzePicture reicht model an checkAnalysis(raw, model) weiter, und readInfo nutzt nur data. Neu in der Edge Function sind nur zwei optionale Parameter: temperature (0–1, Standard 0,2; die Teil-Analyse schickt 0) und model (erzwingt ein bestimmtes Modell ohne Ersatz). model wird nur angenommen, wenn die Nutzer-ID in der Liste aus dem Secret KI_EVAL_USERS steht, also nur für das Testkonto beim Eval. Sonst wird der Parameter ignoriert.

6.4 Übernahme ins Formular

  • Neue Formularfelder: profile: Profile, confidence: Confidence, aiMeta: Meta | null (Meta = { v: 2; prompt: string; model: string | null; at: string; source: 'image' | 'image+page' | 'image+screenshot' | 'image+label' }, source seit 19.11.2026, siehe 6.7).
  • applyAnalysis füllt den Steckbrief wie bisher (nur leere oder offene Felder, Markierung in aiPending) und ersetzt danach immer profile, confidence und aiMeta komplett. Profil-Felder kommen nicht in aiPending.
  • aiMeta bleibt null, wenn in dieser Sitzung keine Analyse lief. Dann bleibt das gespeicherte meta unverändert.
  • Info ersetzt nie das Profil (19.11.2026): applyInfo (Shopseite, Screenshot, Etikett, Bestellung) füllt nur Steckbrief, Kauf, Größe und Pflege. profile, confidence und aiMeta bleiben unverändert – sie kommen allein aus der Bildanalyse. (Vorher überschrieb applyInfo → applyAnalysis das Bild-Profil mit dem leeren Profil der Seitenauswertung.)

6.5 Kategoriewechsel

Wie im Steckbrief („versteckte Werte bleiben gespeichert“, Spec 8a) bleiben Profil-Werte beim Kategoriewechsel gespeichert, werden aber nicht mehr angezeigt oder ausgewertet. Oberfläche, Steckbrief und matchTraits lesen dafür ausschließlich activeProfile(profile, ctx). Wechselt der Nutzer zurück, sind die Werte wieder da.

6.6 Speicherung

items.analysis (jsonb, seit 0001) enthält Altdaten aus dem Import (vdesc, matInfo, extra …). Diese bleiben erhalten.

  3. Neues Teil: analysisBase = {}.
  4. Quelle: meta.source sagt, was in die Bildanalyse einging: image (nur das Bild), image+page (Text der Produktseite per Link), image+screenshot (Screenshot eines Shops oder einer Bestellung), image+label (Etikett). Ältere Einträge ohne source gelten als image.
  5. Gleichzeitiges Bearbeiten desselben Teils ist bei zwei Nutzern selten. Es gilt wie bei allen anderen Feldern: Wer zuletzt speichert, gewinnt. Deshalb ist keine RPC und keine Migration nötig.

  1. Ablauf „Neues Teil“: Foto → Freistellen → „Passt das so?“ → „Hast du noch weitere Infos?“ mit Link einfügen · Screenshot oder Etikett · Weiter ohne → Formular. Beim Start über einen Link (Produktseite schon geladen) entfällt der Schritt. Ohne Foto gibt es keinen Schritt und keine Bildanalyse.
  2. Reihenfolge: Erst die Info auslesen (readPage für den Seitentext, readInfo für Screenshot/Etikett; die KI erkennt die Art selbst, Feld kind), sofort ins Formular übernehmen, dann eine Bildanalyse. Die ausgelesenen Fakten gehen als Kontext mit (infoContext, als text an die Edge Function, die ihn hinter den Prompt hängt): Name, Kategorie, Farben, Muster, Material mit Prozent, Passform (Begriffe aus Name und Beschreibung, genannte Stufen), Beschreibung der Seite gekürzt auf 1500 Zeichen. Überschrift „Angaben des Shops, verlässlicher als das Foto:“ bzw. „Angaben vom Etikett, verlässlicher als das Foto:“.
  3. Rangfolge (reine Funktion mergeSources in packages/core/src/ai/merge.ts), gilt für die Steckbrief-Felder: Nutzer (bestätigt) > Etikett > Shopseite/Screenshot > Begriffe im Namen (fitFromName) > Bildschätzung. Bestätigt = gesetzt und nicht in aiPending. Die Quellen werden von unten nach oben angewendet; jede darf leere und unbestätigte Felder füllen, auch die, die eine rangniedrigere Quelle gerade vorgeschlagen hat. Die Passform zählt je Stufe: Begriffe im Namen ersetzen nur Stufen, die Shop oder Etikett nicht selbst nennen. Kauf, Größe und Pflege kommen nur aus den Infos (Etikett vor Shop).
  4. Profil (profile, confidence, aiMeta) kommt immer aus der Bildanalyse; ohne Bild bleibt es, wie es ist. Der Beinverlauf aus dem Namen („Straight Leg“, „Tapered“) ersetzt profile.leg.
  5. „Neu analysieren“ (bestehende Teile): Die bestätigten Steckbrief-Werte gehen als Kontext mit (confirmedContext: Name, Kategorie, Farben, Muster, Material, Passform), damit das Profil zu ihnen passt. Der Stapellauf „Profile ergänzen“ schickt keinen Kontext.

Eine Quelle ersetzt einen offenen Wert nur bei gleichem oder höherem Rang (ORIGIN_RANK). Bestätigte Felder verlieren ihren Eintrag. Der zweite Schritt bei „Neues Teil“ führt nur noch das Bild zusammen (used für meta.source), damit Eingaben des Nutzers in der Zwischenzeit nicht zurückgedreht werden. Eine von der KI gesetzte Kategorie leert nie eine bestätigte Größe.
